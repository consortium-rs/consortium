# TEE SDK Design Document

## Overview

A Rust macro-based SDK for building OP-TEE Trusted Applications (TAs) with ergonomic, type-safe APIs on both the TA (secure world) and CA (normal world) sides. Built on top of Apache Teaclave TrustZone SDK (`optee_utee` / `optee_teec`).

The core idea: the developer writes normal Rust functions, and the SDK generates all OP-TEE plumbing — parameter packing/unpacking, command dispatch, and the CA-side calling stubs.

---

## Workspace Structure

```
workspace/
├── tee-macros/          # proc-macro crate: #[tee_function], tee_service!
├── tee-common/          # shared type matchers, slot assignment logic
│
├── my-ta/               # Trusted Application
│   ├── Cargo.toml       # [lib] (rlib) + [[bin]] (cdylib)
│   ├── build.rs         # optee_utee_build: UUID, TA properties, user_ta_header
│   └── src/
│       ├── lib.rs       # tee_service! + #[tee_function] definitions — CA-facing API
│       └── main.rs      # #![no_main], use my_ta::*, include!(OUT_DIR/user_ta_header.rs)
│
└── my-ca/               # Client Application
    ├── Cargo.toml       # depends on my-ta (the rlib)
    └── src/
        └── main.rs      # uses generated call_function_a(), call_function_b(), etc.
```

### Cargo.toml for the TA crate

```toml
[features]
ca = []    # enabled by the CA when depending on this crate
           # must NOT be enabled in the TA binary build

[lib]
crate-type = ["rlib"]     # linked by CA

[[bin]]
name = "ta"
crate-type = ["cdylib"]   # loaded by TEE OS
```

The CA depends only on the `rlib` target, which compiles for the host architecture using `optee_teec`. The `cdylib` binary compiles for the secure world using `optee_utee`.

The `ca` feature flag gates all CA-side generated code. The TA binary build never enables it, so `call_*` stubs are not compiled into the secure-world binary. The CA enables it explicitly:

```toml
# my-ca/Cargo.toml
[dependencies]
my-ta = { path = "../my-ta", features = ["ca"] }
```

## Crate Targets and Dependencies

| Target | Crate | Key dependency |
|--------|-------|---------------|
| TA binary (`cdylib`) | `my-ta` (bin) | `optee_utee` (secure world) |
| CA library (`rlib`) | `my-ta` (lib) | `optee_teec` (normal world) |
| CA application | `my-ca` | `my-ta` (rlib) |

`lib.rs` only imports `optee_teec` so it compiles cleanly for the host. `main.rs` imports `optee_utee` for the secure-world entry points.

## Developer Experience

### What the developer writes

```rust
// my-ta/src/lib.rs

#[tee_function]
pub fn function_a(count: u32, data: &[u8]) -> Result<()> {
    // business logic
}

#[tee_function]
pub fn function_b(input: (u32, u32), out: &mut [u8]) -> Result<()> {
    // business logic
}

tee_service! {
    functions {
        function_a,
        function_b,
    },
}
```

```rust
// my-ta/src/main.rs
#![no_main]

use my_ta::*;

include!(concat!(env!("OUT_DIR"), "/user_ta_header.rs"));
```

```rust
// my-ca/src/main.rs

fn main() -> Result<()> {
    let mut ctx = Context::new()?;
    let uuid = Uuid::parse_str("...")?;
    let mut session = ctx.open_session(uuid)?;

    // Generated by tee_service! — normal Rust function call
    my_ta::call_function_a(&mut session, 42, &my_data)?;
    my_ta::call_function_b(&mut session, (1, 2), &mut out_buf)?;
    Ok(())
}
```

### What gets generated

**`#[tee_function]`** generates per function:

- `pub(crate) fn function_a_dispatched(...)` — TA-side unpacking wrapper, always compiled, crate-private
- `#[cfg(feature = "ca")] pub fn call_function_a(...)` — CA-side calling stub, only compiled when `ca` feature is enabled

**`tee_service!`** generates centrally:

- `pub enum Command { FunctionA, FunctionB }` — command ID enum
- `pub(crate) fn invoke_command(cmd: u32, params: &mut Parameters) -> Result<()>` — TA dispatch entry point

## Macro Design

### `#[tee_function]`

An attribute macro applied to individual functions in `lib.rs`. It generates three things from one function definition:

1. The original function — untouched
2. `pub(crate) fn function_a_dispatched(...)` — always compiled, used by `tee_service!` dispatch, invisible outside the crate
3. `#[cfg(feature = "ca")] pub fn call_function_a(...)` — compiled only when the `ca` feature is enabled; dead in the TA binary

```rust
// Input
#[tee_function]
pub fn function_a(count: u32, data: &[u8]) -> Result<()> { ... }

// Generated (1): TA-side dispatch wrapper — always present, crate-private
pub(crate) fn function_a_dispatched(params: &mut Parameters) -> Result<()> {
    let count: u32 = unsafe { params.0.as_value()?.a() };
    let data: &[u8] = unsafe { params.1.as_memref()?.buffer() };
    function_a(count, data)
}

// Generated (2): CA-side calling stub — only with `ca` feature
#[cfg(feature = "ca")]
pub fn call_function_a(session: &mut Session, count: u32, data: &[u8]) -> Result<()> {
    let p0 = ParamValue::new(count, 0, ParamType::ValueInput);
    let p1 = ParamTmpRef::new_input(data);
    let mut op = Operation::new(0, p0, p1, ParamNone, ParamNone);
    session.invoke_command(Command::FunctionA as u32, &mut op)
}
```

### `tee_service!`

A function-like macro in `lib.rs`. Its sole responsibility is generating the `Command` enum and the `invoke_command` dispatch — CA stubs are now the responsibility of `#[tee_function]`.

```rust
// Generated
pub enum Command {
    FunctionA = 0,
    FunctionB = 1,
}

pub(crate) fn invoke_command(cmd: u32, params: &mut Parameters) -> Result<()> {
    match cmd {
        x if x == Command::FunctionA as u32 => function_a_dispatched(params),
        x if x == Command::FunctionB as u32 => function_b_dispatched(params),
        _ => Err(Error::new(ErrorKind::BadParameters)),
    }
}
```

### Lifecycle hooks in `tee_service!`

The `triggers` block (future work) maps hook names to user functions. Hook names are **strictly fixed** — they must match the GlobalPlatform lifecycle entry point names exactly. The macro enforces this at compile time and rejects any unknown hook name.

```rust
tee_service! {
    functions {
        function_a,
        function_b,
    },
    triggers {
        // Hook names are fixed — these are the only valid identifiers:
        on_create:        my_create,
        on_open_session:  my_open,
        on_close_session: my_close,
        on_destroy:       my_destroy,
    },
}
```

| Hook name | GP entry point | Signature enforced |
|---|---|---|
| `on_create` | `TA_CreateEntryPoint` | `fn() -> Result<()>` |
| `on_open_session` | `TA_OpenSessionEntryPoint` | `fn(params: &mut Parameters) -> Result<()>` |
| `on_close_session` | `TA_CloseSessionEntryPoint` | `fn()` |
| `on_destroy` | `TA_DestroyEntryPoint` | `fn()` |

The user function's signature must match exactly — a mismatch is a compile error, not a runtime error.

## Parameter Type Mapping

Slot assignment is sequential by argument order. The same ordering is used by both the TA unpacking and the CA packing, so they are guaranteed to agree.

| Rust type | GP TEE type | Direction | TA unpacks via | CA packs via |
|-----------|-------------|-----------|----------------|--------------|
| `bool` | `VALUE_INPUT` | in | `.as_value()?.a() != 0` | `ParamValue::new(x as u32, 0, ValueInput)` |
| `u32` | `VALUE_INPUT` | in | `.as_value()?.a()` | `ParamValue::new(x, 0, ValueInput)` |
| `(u32, u32)` | `VALUE_INPUT` | in | `.as_value()?.a(), .b()` | `ParamValue::new(a, b, ValueInput)` |
| `&mut (u32, u32)` | `VALUE_OUTPUT` | out | local mut + flush | `ParamValue::new(0, 0, ValueOutput)` + read back |
| `&[u8]` | `MEMREF_INPUT` | in | `.as_memref()?.buffer()` | `ParamTmpRef::new_input(x)` |
| `&mut [u8]` | `MEMREF_OUTPUT` / `INOUT` | out/inout | `.as_memref()?.buffer_mut()` | `ParamTmpRef::new_output(x)` |

---

## Slot Assignment ABI

Slots are assigned left-to-right from the function signature. Both the TA dispatch wrapper and the CA calling stub are generated from the same signature, so slot order is always consistent — the developer never coordinates slot indices manually.

OP-TEE supports up to 4 parameter slots per invocation. The macro panics at compile time if a function has more than 4 parameters.

## TA Build (`build.rs`)

The TA's `build.rs` uses `optee_utee_build` (existing Teaclave tooling) to handle UUID registration and generate `user_ta_header.rs`:

```rust
// my-ta/build.rs
use optee_utee_build::{Error, RustEdition, TaConfig};

fn main() -> Result<(), Error> {
    let config = TaConfig::new_default_with_cargo_env("12345678-1234-1234-1234-123456789abc")?;
    optee_utee_build::build(RustEdition::Before2024, config)
}
```

The UUID lives here and nowhere else. It is not part of `tee_service!`.

---

## Lifecycle Hooks (`tee_lifecycle!`) — Future Work

Lifecycle hooks are declared inside `tee_service!`'s `triggers` block (see Macro Design above) rather than as a separate macro. The `tee_lifecycle!` name is reserved for potential standalone use but the primary interface is via `triggers { }`.

Hook names are a **closed set** — only the four GlobalPlatform entry point names are valid. The macro performs name validation at compile time.

## Implementation Roadmap

| Step | What | Crate |
|------|------|-------|
| 1 | Type matchers (`is_primitive`, `is_slice_ref`, etc.) | `tee-common` |
| 2 | `gen_unpack` — TA-side parameter unpacking codegen | `tee-common` |
| 3 | `gen_pack` — CA-side parameter packing codegen | `tee-common` |
| 4 | `#[tee_function]` — `_dispatched` + `#[cfg(feature="ca")] call_*` | `tee-macros` |
| 5 | `tee_service!` — `Command` enum + `invoke_command` dispatch | `tee-macros` |
| 6 | `tee_service! { triggers { } }` — lifecycle hook dispatch | `tee-macros` |
