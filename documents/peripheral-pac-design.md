# Peripheral Configuration & PAC Generation Design

**Status:** Proposal  
**Date:** 2026-04-06

---

## Overview

This document proposes a system for declaring peripheral ownership in `Consortium.toml` and automatically generating:

1. **RIF/RIFSC security configuration** for STM32MP2x (or equivalent isolation units on i.MX 9x) in M-core secure firmware.
2. **PAC peripheral objects** (`p.I2C1`, `p.SPI2`, …) for M-core firmware, exposed in `embedded-hal`-compatible format backed by `embassy-stm32` or `imxrt-hal`.
3. **Device Tree Source (DTS) fragments** assigning the remaining peripherals to Linux or OP-TEE.

The goal is that a developer declares intent once and the build system derives safe, non-overlapping peripheral access across all execution environments.

---

## Motivation

On a heterogeneous SoC such as the STM32MP257 (Cortex-A35 + Cortex-M33 + Cortex-M0+) or i.MX 93 (Cortex-A55 + Cortex-M33), each peripheral must be owned by exactly one execution domain:

| Domain | Mechanism | Current approach |
|--------|-----------|-----------------|
| Linux (NS) | DTS `status = "okay"` | Manual |
| OP-TEE (S) | DTS `secure-status = "okay"` | Manual |
| M-core NS firmware | PAC + HAL + RIFSC | Manual |
| M-core S firmware (TF-M) | PAC + HAL + RIFSC | Manual |

Today all four configurations are written by hand and must stay in sync. A mismatch causes silent mis-attribution of interrupts, broken DMA, or a security violation trap at runtime.

Consortium.toml should become the single source of truth.

## Consortium.toml Schema

### Example

```toml
[general]
chip = "stm32mp257"

[project]
name = "my-app"

# ── M-core firmware entries (existing) ────────────────────────────────────────
[project.firmware.sensor_fw]
core     = "CortexM33"
index    = 0
path     = "firmware/sensor"

[project.firmware.motor_fw]
core     = "CortexM0p"
index    = 1
path     = "firmware/motor"

# ── Peripheral assignments (new) ──────────────────────────────────────────────

[[peripherals]]
name      = "I2C1"
owner     = "CortexM33"          # firmware key or "linux" / "optee"
security  = "non-secure"         # "secure" | "non-secure" | "secure-privileged"
rif_cid   = 2                    # RIF Compartment ID (STM32MP2x only; omit for i.MX)
dma       = ["GPDMA1_CH0"]       # optional: claim DMA channels alongside

[[peripherals]]
name      = "SPI2"
owner     = "CortexM0p"
security  = "non-secure"
rif_cid   = 3

[[peripherals]]
name      = "UART4"
owner     = "linux"
# No rif_cid/security needed; will appear in DTS only

[[peripherals]]
name      = "I2C5"
owner     = "optee"
security  = "secure"
rif_cid   = 1

[[peripherals]]
name      = "LPTIM1"
owner     = "CortexM33"
security  = "secure"             # TF-M / secure M-core partition
rif_cid   = 2
```

### Field reference

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `name` | string | yes | Peripheral name matching the chip's PAC (case-insensitive, e.g. `"I2C1"`) |
| `owner` | string | yes | `"linux"`, `"optee"`, or the firmware key from `[project.firmware.*]` |
| `security` | string | when owner is M-core | `"non-secure"` \| `"secure"` \| `"secure-privileged"` |
| `rif_cid` | u8 | STM32MP2x only | RIF Compartment ID (1–7); must match the CID assigned to the owning core |
| `dma` | [string] | no | DMA channel names to co-assign alongside the peripheral |

## Output Artifacts

### 1. RIFSC / RIF Configuration (`consortium-pac` / `consortium-runtime-mcu`)

For STM32MP2x, the RIFSC (Resource Isolation Framework Security Controller) controls per-peripheral:
- `RIFSC_PRIVx` — privileged access bit
- `RISFSC_SECx` — secure-world bit  
- `RIFSC_CIDCFGRx` — compartment ID assignments

The generator will emit a Rust init function (called from `consortium-runtime-mcu` startup):

```rust
// Generated: src/rif_config.rs
// DO NOT EDIT — regenerated by `consortium build`

use crate::pac::RIFSC;

pub fn configure_rifsc(rifsc: &mut RIFSC) {
    // I2C1: owner=CortexM33, cid=2, non-secure
    rifsc.privcfgr1().modify(|_, w| w.priv8().clear_bit());
    rifsc.seccfgr1().modify(|_, w| w.sec8().clear_bit());
    rifsc.risc_cidcfgr8().write(|w| unsafe {
        w.cfen().set_bit().scid().bits(2)
    });

    // SPI2: owner=CortexM0p, cid=3, non-secure
    rifsc.privcfgr1().modify(|_, w| w.priv15().clear_bit());
    rifsc.seccfgr1().modify(|_, w| w.sec15().clear_bit());
    rifsc.risc_cidcfgr15().write(|w| unsafe {
        w.cfen().set_bit().scid().bits(3)
    });

    // LPTIM1: owner=CortexM33, cid=2, secure
    rifsc.privcfgr5().modify(|_, w| w.priv40().clear_bit());
    rifsc.seccfgr5().modify(|_, w| w.sec40().set_bit());
    rifsc.risc_cidcfgr40().write(|w| unsafe {
        w.cfen().set_bit().scid().bits(2)
    });
}
```

For i.MX 9x, the equivalent TRDC (Trusted Resource Domain Controller) configuration will be emitted instead.

### 2. PAC Peripheral Tokens (`consortium-pac`)

A new crate `consortium-pac` is generated per chip/config combination. It wraps the upstream PAC (e.g., `stm32mp257-pac` or `imxrt1060`) and exposes only the peripherals owned by each firmware target as a `Peripherals` struct:

```rust
// Generated for firmware/sensor (CortexM33)
// consortium-pac/src/sensor_fw.rs

pub struct Peripherals {
    pub i2c1:   embassy_stm32::peripherals::I2C1,
    pub lptim1: embassy_stm32::peripherals::LPTIM1,
    // DMA channel claimed alongside I2C1:
    pub gpdma1_ch0: embassy_stm32::peripherals::GPDMA1_CH0,
}

impl Peripherals {
    /// # Safety
    /// Must be called exactly once, after `configure_rifsc()`.
    pub unsafe fn steal() -> Self {
        let p = embassy_stm32::Peripherals::steal();
        Self {
            i2c1:        p.I2C1,
            lptim1:      p.LPTIM1,
            gpdma1_ch0:  p.GPDMA1_CH0,
        }
    }
}
```

Access in firmware:

```rust
#[embassy_executor::main]
async fn main(_spawner: Spawner) {
    consortium_runtime_mcu::init_rifsc();  // generated call

    let p = unsafe { sensor_fw::Peripherals::steal() };

    let mut i2c = I2c::new(
        p.i2c1,
        p.gpdma1_ch0,
        Config::default(),
    );

    loop {
        let mut buf = [0u8; 2];
        i2c.read(0x48, &mut buf).await.unwrap();
        // ...
    }
}
```

For i.MX 9x the types are drawn from `imxrt-hal` instead of `embassy-stm32`.

### 3. Device Tree Fragments

The generator appends `&fragment { status = "okay"; }` (or `secure-status`) stanzas to a base DTS for the peripherals assigned to Linux or OP-TEE.

Example output for the config above:

```dts
/* Generated: overlay/linux-peripherals.dtsi */
/* DO NOT EDIT — regenerated by `consortium build` */

&uart4 {
    status = "okay";
    pinctrl-names = "default";
    /* pinctrl left to base board file */
};

/* Generated: overlay/optee-peripherals.dtsi */

&i2c5 {
    secure-status = "okay";
};
```

These fragments are included by the top-level DTS via `#include`.

## Architecture

```
Consortium.toml
      │
      ▼
consortium-common (parse + validate PeripheralEntry list)
      │
      ├──▶ consortium-pac-gen  (new crate, build-time binary)
      │          │
      │          ├── rif_config.rs  ──▶ consortium-runtime-mcu (M-core startup)
      │          ├── <fw_key>.rs    ──▶ consortium-pac/<fw_key>  (per-firmware PAC wrapper)
      │          └── linux-peripherals.dtsi / optee-peripherals.dtsi
      │
      └──▶ consortium-builder (orchestrates code generation as a build step)
```

### New crate: `consortium-pac-gen`

A build-time binary (or `build.rs` helper library) that:

1. Reads `Consortium.toml` via `consortium-common`.
2. Validates ownership uniqueness (no peripheral claimed by two owners).
3. Validates that all referenced peripheral names exist in the chip's register map (using metadata from a chip-specific database, see below).
4. Emits the three artifact types described above into `OUT_DIR` or a designated `generated/` directory.

### Chip peripheral database

A lightweight JSON/TOML file per supported chip enumerating peripheral names, their RIFSC index, their DTS node name, and their HAL type path. Initially provided for:

- STM32MP257 (via `stm32mp-data` or extracted from CubeMX IP database)
- i.MX 93 (via NXP SDK metadata or `imxrt-ral`)

The database lives in `consortium-pac-gen/data/<chip>.toml` and is embedded at compile time via `include_str!`.

---

## Validation Rules

The generator enforces at build time:

1. **Uniqueness:** Each peripheral has exactly one owner.
2. **CID consistency:** All peripherals owned by the same firmware key use the same `rif_cid`.
3. **Security consistency:** A peripheral marked `secure` cannot be owned by a Linux or non-secure firmware owner.
4. **DMA co-ownership:** DMA channels claimed under `dma = [...]` must not be claimed by any other peripheral entry.
5. **Name validity:** All names must exist in the chip database.
6. **Core availability:** The owning firmware's `core` field must be compatible with the chip (e.g., a CortexM0p cannot exist on a chip that only has a CortexM33).

Errors are emitted as `cargo:error=` messages and abort the build with a human-readable description.

## HAL Strategy

### STM32MP2x — embassy-stm32

`embassy-stm32` already supports STM32MP2x and provides `embassy_executor`, peripheral types, and async HAL drivers. The generated `Peripherals::steal()` calls `embassy_stm32::Peripherals::steal()` and destructures only the owned subset.

Dependency in firmware's `Cargo.toml`:

```toml
[dependencies]
embassy-executor   = { version = "0.7", features = ["arch-cortex-m", "executor-thread"] }
embassy-stm32      = { version = "0.2", features = ["stm32mp257fai", "time-driver-any"] }
consortium-pac     = { path = "../../generated/pac/sensor_fw" }
```

### i.MX 9x — imxrt-hal

`imxrt-hal` (and `imxrt-ral`) provide register-level and HAL-level access for NXP i.MX RT/9x series. The generated struct wraps `imxrt_hal::instance::*` tokens.

Dependency in firmware's `Cargo.toml`:

```toml
[dependencies]
imxrt-hal  = { version = "0.5", features = ["imxrt93"] }
imxrt-ral  = { version = "0.5", features = ["imxrt93"] }
consortium-pac = { path = "../../generated/pac/sensor_fw" }
```

## Implementation Plan

### Phase 1 — Schema & Validation (1 week)

- [ ] Add `PeripheralEntry` struct to `consortium-common`.
- [ ] Parse `[[peripherals]]` table in `Config::from_toml()`.
- [ ] Implement validation rules 1–6 in `Config::validate_peripherals()`.
- [ ] Unit tests for each error case.

### Phase 2 — Chip Database (1 week)

- [ ] Define `ChipPeripheralDb` schema (TOML, embedded).
- [ ] Populate STM32MP257 database (RIFSC index, DTS node, HAL type path, DMA channels).
- [ ] Populate i.MX 93 database (TRDC index, DTS node, HAL type path).
- [ ] CLI helper: `consortium list-peripherals --chip stm32mp257` to dump DB.

### Phase 3 — Code Generation (2 weeks)

- [ ] Create `consortium-pac-gen` crate (binary + library API).
- [ ] Implement RIFSC config emitter (STM32MP2x path).
- [ ] Implement TRDC config emitter (i.MX 9x path).
- [ ] Implement per-firmware PAC wrapper emitter.
- [ ] Implement DTS fragment emitter (linux + optee overlays).
- [ ] Wire into `consortium-builder` as a pre-build step.

### Phase 4 — Runtime Integration (1 week)

- [ ] `consortium-runtime-mcu`: call generated `init_rifsc()` / `init_trdc()` during startup.
- [ ] Example firmware using generated `Peripherals` struct with embassy-stm32.
- [ ] Example firmware using generated `Peripherals` struct with imxrt-hal.
- [ ] Integration test: build full config, verify generated files compile.

### Phase 5 — DTS Integration (1 week)

- [ ] Hook DTS fragment generation into `consortium-builder` build pipeline step 1.
- [ ] Verify DTS overlays compile with `dtc`.
- [ ] Document how to include overlays in the base board DTS.

## Open Questions

1. **Pin multiplexing (pinctrl):** Should Consortium.toml also declare pin assignments so that DTS `pinctrl` nodes can be generated? This is a significant scope increase but would eliminate another manual sync point.

2. **Clock configuration:** Peripherals often require specific clock sources to be enabled. Should the generator also emit RCC/CCM clock enable calls?

3. **Interrupt routing:** On STM32MP2x, EXTI and NVIC routing for M-core peripherals must be configured. Should this be part of the generated init code?

4. **Version-locked chip databases:** The peripheral DB must match the exact silicon revision. How do we handle multi-revision chips (e.g., STM32MP257 rev A vs rev B)?

5. **embassy-stm32 feature alignment:** `embassy-stm32` requires a feature flag per chip variant. The build system must propagate the correct feature from `Chip` enum to the downstream crate.

---

## Non-Goals

- This proposal does **not** aim to replace `embassy-stm32` or `imxrt-hal`; it wraps them.
- This proposal does **not** generate full DTS board files; it generates peripheral assignment overlays that include into an existing board DTS.
- This proposal does **not** handle clock tree configuration in this iteration (see open questions).
- This proposal does **not** support arbitration of shared peripherals (e.g., a bus shared between cores at runtime); each peripheral must have a single static owner.
